# Windows 3.11 on the 192

A PC emulated on the 192's SH-4, running MS-DOS 6.22 and Windows 3.11
from a disk image on an SD card: a bare-metal program of the SDK, like
Doom (`docs/doom.md`), with nothing of the stock software under it.  The
PC is [Tiny386](https://github.com/hchunhui/tiny386) (a 486 with a PC's
chipset, VGA and IDE disk, BSD-3-Clause), made to run on a big-endian CPU
with no operating system (`win311/patches`), with
[SeaBIOS](https://www.seabios.org/) (LGPL-3) as its BIOS.

Neither Tiny386 nor SeaBIOS is in the repository: `win311/build.sh`
downloads both, pinned, and checks them.  Nor is any of Windows or
MS-DOS: the disk image is made from your own floppies
(`win311/install.py`) and stays outside the repository (`win311/work/` is
ignored).

## The card

| file | what | made by |
|------|------|---------|
| `WIN311.BIN` | the first stage, `win311/pcboot`: what sdboot's menu lists | `win311/build.sh` |
| `PCEMU.BIN` | the emulator (Tiny386 and `win311/port` on the SDK) | `win311/build.sh` |
| `BIOS.ROM`, `VGABIOS.ROM` | SeaBIOS and its VGA BIOS, as Tiny386 configures them | `win311/build.sh` |
| `WIN311.IMG` | the hard disk: MS-DOS 6.22 and Windows 3.11 | `win311/install.py` |

The ROMs are not called `.BIN`, so that sdboot's menu does not list
them.  Started from the SD loader (`docs/sd-loader.md`) like any program
on the card.

## Making the disk

```sh
win311/install.py "MS-DOS 6.22 floppies/" "Windows 3.11 floppies/"   # -> win311/work/img/WIN311.IMG
```

QEMU (`qemu-system-i386`) installs from the floppy images, with Setup
typed through its monitor, each step when the screen has stood still
(screendumps of every step beside the image, `install-shots/`): DOS
Setup partitions and formats the disk (64 MiB: 130 cylinders, 16 heads,
63 sectors, the geometry Tiny386 and QEMU both give a disk of that
size) and copies DOS from its three floppies.  Windows' six disks are
then copied to `C:\WININST` with mtools and its Express Setup runs from
there (no printer, no tutorial), since from floppies it asks for the
disks in an order that depends on how fast it runs; the folder is
removed afterwards.  Then the changes for the 192
(`win311/docker/settings.sh`):

* `WIN` at the end of `AUTOEXEC.BAT`: straight to Windows;
* `HIMEM.SYS /TESTMEM:OFF` and `SWITCHES=/F` in `CONFIG.SYS`: no test of
  the 15 MB of extended memory (25 s of the unit's time at the emulated
  PC's pace) and no two seconds' wait for F5/F8;
* `Paging=No` in `SYSTEM.INI`'s `[386Enh]`: no swap file (it would only
  fill the RAM the disk's writes go to, below).

Windows runs in 386 enhanced mode with 16 MiB.  Docker's file sharing
on a Mac can show a container a file as it was before QEMU last wrote
it, which spoilt an image here once: `install.py` passes the image
through the container by a pipe instead.

## The disk on the card

The image is read as the PC needs it (`win311/port/disk.c`: `sd_open`
walks its chain of clusters once, `sd_pread` reads 4 KiB at a time) and
kept in RAM, 31 MiB of it.  **What the PC writes stays in RAM**: the
card is never written (the kit cannot write to a card yet), so changes
last until the PC is left or the unit switched off.  When the RAM is
full, sectors read but never written make room; when nothing but
written ones is left, a write fails as a full disk would.

Going from power-on to Program Manager reads about 2.3 MB of the image
(571 reads of 4 KiB, measured on the host build) and writes one sector.

## Memory

| from | to | what |
|------|----|------|
| 0x8c00f000 | | the hand-off block (`win311/pcboot/handoff.h`) |
| 0x8c010080 | 0x8c400000 | `PCEMU.BIN` (`sdk/link.ld` with LOAD 0x8c010000, SIZE 0x3f0000), its bss, its stack at the top |
| 0x8c7c0000 | 0x8c800000 | `sdboot`'s session, untouched |
| 0x8c800000 | 0x8d800000 | the PC's RAM, 16 MiB |
| 0x8d800000 | 0x8df00000 | the heap: the frame buffer (720x480, 32 bits), VGA memory (256 KiB), the ROMs, the disk's map |
| 0x8df00000 | 0x8df20000 | `pcboot`, for the way back |
| 0x8e000000 | 0x8ff00000 | the disk's sectors in RAM (31 MiB) |

## The picture

The 192's screen is 400x235 of 8 bits through a palette; the PC's is
640x480 in Windows.  `win311/port/screen.c` uses a fixed palette of six
levels a channel (0, 64, 128, 160, 192, 255: Windows' 16 colours exact,
the others for averages) and 40 greys, and has two ways of drawing,
SETUP switching between them:

* **scaled** (at the start): the whole picture, each pixel of the 192's
  the average of the PC's it covers.  Windows' text is just readable;
  icons and windows are clear.
* **1:1**: a 400x235 part of the picture, pixel for pixel, following
  the pointer.

Windows' mode (12h: 16 colours in four planes) is scaled straight from
the VGA's memory, without Tiny386 drawing anything: eight pixels across
become five (weights in fifths of a pixel), the two or three lines a
row covers are weighted 2 2 or 1 2 1 (no line is dropped, so one-pixel
lines stay), and the weights of each pixel add up to 32, so there is no
division.  Only the groups of eight pixels whose planes changed since
the last picture are drawn again, every 60 ms at most, and only the
rows that changed go to the screen.  Anything else (DOS's text, the 1:1
view) goes by way of Tiny386's frame buffer of 32 bits a pixel, scaled
by area averaging every 250 ms, and only when a sum over the frame
buffer says it changed.  The first version scaled the frame buffer
every 80 ms with three divisions a pixel: that took three quarters of
the SH-4's time (`__udivsi3` alone 27%).

## The controls

| control | the PC |
|---------|--------|
| volume knob | the mouse across (louder: right) |
| select knob | the mouse up and down (clockwise: down) |
| pressing the select knob (SELECT) | the left button, held as long as it is |
| top right soft key | the right button |
| bottom left / bottom right soft key | Enter / Esc |
| NEXT | Tab |
| PREV | Alt+Tab |
| SETUP | scaled ⇄ 1:1 |
| RETURN held 2 s | back to the SD loader (as everywhere) |

A detent is 2 mouse steps, 4 when the knob turns fast (3 or more
detents between two looks, every 20 ms); Windows' own acceleration
(MouseThreshold1/2, MouseSpeed) doubles larger reports.  In the
emulator, ten slow detents of either knob move the pointer about 20
pixels of the PC's.  The display key and CD EJECT work as everywhere.

## The clock

The kit knows no calendar of the unit's, so the PC's clock starts at
1 January 1994, 00:00, and runs from there.

## Building and checking

```sh
win311/build.sh                 # win311/out: WIN311.BIN, PCEMU.BIN, BIOS.ROM, VGABIOS.ROM
win311/host.sh                  # win311/work/host/pcemu-host: the same PC on the Mac
win311/work/host/pcemu-host --shot 20000:desk.png --small 20000:desk-192.png tiny386.ini
win311/be-test.sh WIN311.IMG    # the same PC on a big-endian CPU (MIPS, qemu-user, docker)
```

`pcemu-host` runs the same patched Tiny386 with the same disk layer and
screen conversion (`--small` writes what the 192 would show), without
the SDK.  `be-test.sh` builds it for a big-endian MIPS as well and
compares the two's screens at fixed points of instruction-counted time
(`--virtual`): on the Mac, at 3 s and 30 s, they are the same, the
second Program Manager.

The end-to-end test, with the stock software starting sdboot from a
disc, sdboot starting `WIN311.BIN` from the emulated card, and the
caches modelled:

```sh
PATH=$PWD/sdk/tools/sh4-docker:$PATH RNSE_DISC=disc.iso RNSE_WIN311=dir \
    cargo test --release -p rnse-ports --test disc win311 -- --nocapture
```

`dir` holds `win311/out`'s files and `WIN311.IMG`; screenshots go to
`out/win311/`.

## Speed

In the emulator of the 192 (one SH-4 instruction a cycle at 235 MHz,
caches modelled): **Program Manager about 40 s after `PCEMU.BIN`
starts**: SeaBIOS and its VGA BIOS about 10 s, DOS 15 s, Windows' start
15 s.  The PC runs 0.5 to 0.8 million x86 instructions a second in
Windows (a string instruction counted once, however many times it
repeats): some 300 to 450 cycles of the SH-4 an instruction, a slow 286
for Windows.  Windows is usable, slowly: Program Manager's icons take a
few seconds to appear.  Sampled where the SH-4 spends its time while
Windows starts: Tiny386's interpreter (`cpu_exec1` 39%), its address
translation (`translate`, `translate_lpgno` 27%), the screen 4%.
`-O3` is no faster than `-O2`.  The time is read once a pass of the main
loop rather than at each of Tiny386's many calls (`micros()` costs a
division on the SH-4), and the faceplate is looked at every 20 ms.

The emulator counts every SH-4 instruction as one cycle and no cost for
the caches' misses; how fast a unit runs this is not known until one
does.

## What is known, and what is not

* Measured on the host builds: Windows 3.11 boots to Program Manager, on
  a little- and a big-endian CPU alike.
* In the emulator of the 192 (`win311_runs_from_an_sd_card`, caches
  modelled, RAM arbitrary): Windows 3.11 boots from the emulated card to
  Program Manager, the knobs move the pointer the right way, the
  watchdog is served throughout.  Disk: about 550 reads of 4 KiB (2.2
  MB) and one sector written on the way.
* On a unit: nothing yet.
